# 族谱 · 离线桌面版（骨架）

家族自用型族谱工具。**不需要服务器、不需要账号、不需要联网**：双击打开即用，数据就是本机的一个数据库文件，换机器靠「记谱包」导入导出。

当前状态：**可用**——打开 → 看到世系树 → 增删改人物（删除二次确认、级联）→ 年份与干支互转、标注第几世 → 纵向/横向切换布局 → 导出 `.zupu` / PNG / PDF / Excel → 在另一台电脑选锚点导入替换 → 可精确撤销。

## 一、怎么跑起来

### 方式 1：浏览器里试（最快，不用装 Electron）

```bash
cd zupu-app
npm run dev          # 打开 http://127.0.0.1:4173
```

数据落在 `data/zupu-dev.db`，与桌面版完全隔离，随便点。

### 方式 2：当作桌面应用跑

```bash
cd zupu-app
npm install          # 会下载 Electron（约 100MB，仅首次）
npm start
```

### 方式 3：打包成安装包给族人

```bash
npm run dist:win     # Windows：安装版 exe + 便携版 exe（在 Windows 上跑）
npm run dist:mac     # macOS：dmg + zip（在 Mac 上跑）
npm run dist:linux   # Linux：AppImage + deb（在哪都能跑）
npm run dist:dir     # 只出解包目录（快，用来确认能不能打）
```

产出到 `dist/`，包名统一以 `zhupu` 开头（纯 ASCII，避免部分系统/网盘对中文文件名的兼容问题）：Windows 出 `zhupu-Setup-x.y.z.exe`（安装版）与 `zhupu-Portable-x.y.z.exe`（便携版），macOS 出 `zhupu-x.y.z-{arch}.dmg/.zip`，Linux 出 `zhupu-x.y.z-x86_64.AppImage` 与 `zhupu-x.y.z-amd64.deb`。便携版是单文件 exe，插上 U 盘就能用，不写注册表、不写 Program Files，数据跟着 exe 走。

**国内网络必读**：打包时 electron-builder 要下载 Electron 本体（约 124MB）和一套打包工具链。GitHub 直连经常龟速甚至校验失败，先挂镜像再打包：

```bash
export ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/"
export ELECTRON_BUILDER_BINARIES_MIRROR="https://npmmirror.com/mirrors/electron-builder-binaries/"
npm run dist:linux   # 换成对应平台的命令
```

挂了镜像之后实测：124MB 的 Electron 16 秒下完，AppImage + deb 全流程 3 分钟内。

**跨平台规则**：electron-builder 的规矩是「在哪个系统上打哪个系统的包」——Windows 的 nsis/exe 要在 Windows 上打，Mac 的 dmg 要在 Mac 上打（签名与 icns 工具都只有那边有）；Linux 的 AppImage/deb 在哪个系统都能打。所以全平台安装包的产出方式是：三台机器（或三台虚拟机）各跑一条命令，共享同一个仓库即可。`dist:all` 只能同时打出 win + linux。

**为什么全平台可行**：整个应用只有一个运行时依赖——Electron 自带的 Node 22（`node:sqlite` 是内置模块）。没有任何原生编译模块（better-sqlite3 只是备用驱动，未安装），所以不需要 per-platform 的 native rebuild，三平台用的是同一份纯 JS 代码。

数据目录按平台惯例落位：Windows `%APPDATA%/族谱/data`，macOS `~/Library/Application Support/族谱/data`，Linux `~/.config/族谱/data`。菜单一键打开数据文件夹，方便备份。

## 二、跑测试

```bash
npm test             # 端到端：两台电脑各录各的 → 导入替换 → 撤销（40 项断言）
node test/ui.js      # 界面：真实点击、编辑、增删确认、切布局、走完导入向导（32 项断言，需本机有 Chrome）
node test/export.js  # 导出：zupu / PNG / PDF 真落盘校验 + 保存位置选择流程（23 项断言）
node test/features.js # 本轮新功能：干支、级联删除、纵横布局、Excel 结构、照片（74 项断言）
```

四套测试都是**真跑真存**，不是 mock。界面与导出测试会自己起临时库（`data-uitest/`、`data-exporttest/`），不污染你的数据。

想重开一份空谱（旧库自动改名存档，不是删除）：

```bash
npm run reset
```

## 四、几个关键设计决定

### 1. 主键一律 UUID，绝不使用自增 ID

两台电脑各自新增的人如果都是 1、2、3……一合并就全面撞车，谱系直接串掉。
每张表都带 `uuid / device_id / created_at / updated_at / rev / deleted`。

### 2. 设备身份存在库文件**之外**

`device.json` 与数据库同级，记录写入时的主机名。只把 `.db` 拷到笔记本 → 新机器拿不到身份文件，自动换发新 ID；整份文件夹拷过去 → 主机名对不上，也会换发并记下 `rotated_from`。
**这个坑是测试抓出来的**：最初 device_id 只存库内，B 机导出的包会声称自己是 A 机。

### 3. 导入是「锚点整段替换」，不是合并

- 锚点以上（父辈、祖辈）：一个字节都不动
- 锚点本身：身份保留，字段按包内覆盖
- 锚点以下：整段移除，换成包内子树
- 本地独有但包里没有的人：默认删除（执行前必须列出清单）
- 外支的配偶：**只解除婚姻，不删除本人**——否则别支的谱会凭空缺人

### 4. 撤销是「反向操作 + 原样写回」，不是恢复快照

批次里存了导入前的原始行（`before_json`）。为什么必须有它：两台机器本来就从同一份库派生，UUID 完全重合，节点是被**就地覆盖**的，`deleted` 一直是 0，光靠「复活软删除」救不回被覆盖的字段——用户会发现自己刚写的备注被导入悄悄带走且再也回不来。
**这个洞也是测试抓出来的**，现在有断言盯着。

### 5. 世系图用 Canvas

几千节点下 DOM/SVG 会直接卡死。布局用变宽 tidy tree：同父按排行左右排，一人多父（嗣子、兼祧）只在主父下占位，其余父关系画红色虚线。配偶是独立人物记录，界面上贴成本人右侧的配偶框（一对夫妻只保留一个人当节点，否则全被当成配偶、根节点会被筛没）。

### 6. 数据格式先不用 zip

`.zupu` 目前是纯 JSON：可人工核对、可 diff、可直接丢进 git 存档，几千人也就几 MB。要放老照片附件时再切 zip，靠 `manifest.format_version` 区分。

### 7. 导出分三种，各有各的用途

| 格式 | 用途 | 实现 |
|---|---|---|
| `.zupu` | 给另一台电脑导入替换 | 明文 JSON |
| `.png` | 发微信、存档、做展板 | 离屏 canvas 整棵重绘，2×–4× 倍率 |
| `.pdf` | 打印悬挂（A4/A3/A2 横向单页） | 自写 100 行 PDF 生成器，把 JPEG 封进单页 |

两个细节值得记：

- **导出必须重新整棵绘制**，不能截屏。屏幕上的 canvas 只画视口内的节点，直接截屏会得到「当前那一屏」。
- **PDF 不引第三方库**：嵌一张 JPEG 只需要一个 Image XObject 加一个 `cm` 变换矩阵，标准里写得很清楚。多一个库就多一个十年后失效的地方。代价是页面内文字不可选中——这是「图页」，印刷级排版要等谱书模块。
- 界面里**不能用 `window.prompt`**：Electron 渲染进程不支持它（返回 `undefined`），预览面板里的沙箱也会静默拦掉，表现就是「点了按钮毫无反应」。所有需要输入的交互都走页面内的弹窗。

### 8. 保存位置：三级降级，任何一环都不该让文件凭空消失

导出前先问「写到哪」（`beginSave`），再生成文件（`saveFile`）。顺序不能反，原因见下。

| 环境 | 走哪条路 |
|---|---|
| 桌面版 | 系统「另存为」对话框，每次都能改文件夹；记住上次用的目录，下次默认打开这里 |
| 浏览器（Chrome/Edge） | `showSaveFilePicker`，同样是系统级选择框 |
| 浏览器不支持 / 跨域 iframe | `<a download>` 落到下载目录 |
| 下载也被拦 | 服务端写 `<数据目录>/exports/`，结果框里给出完整路径 |

有一个真实的坑值得单独记：**跨域 iframe（预览面板就是）里，保存选择框弹得出来，但真正写入时平台会拒绝**——报错是 `Failed to execute 'createWritable': The request is not allowed by the user agent or the platform in the current context`。「能弹框」和「允许写入」是两回事，前者只说明 API 存在。所以做了两层防御：`pickerUsable()` 检测到跨域 iframe 就干脆不用选择框；就算拿到句柄后写入被拒，也**不报错了事**，继续走「下载 + 服务端留副本」——文件永远要有去处，这是导出的底线。

**必须先选位置、再渲染。** 浏览器的文件选择框只认点击那一刻的用户手势（约 5 秒内有效），而 3× 大图要渲染好几秒。顺序反了，对话框会被拒绝，用户点「导出」后就静默无反应。测试里专门断言了 `picker 时刻 < render 时刻`。

桌面版默认目录记在库内的 `meta` 表（`pref.export_dir`），换台电脑重装程序也不会丢；记的值只是路径，不含任何数据。

### 9. 年份 / 干支 / 原文，三份都留着

谱上写的是「康熙戊寅」，不是 1698。程序填的年份可以算，**谱上的原话不能改**，所以 `person_event` 存三列：`time_text`（原话）、`time_start`（公元年）、`time_ganzhi`（干支），彼此不覆盖。

补齐的优先级是：**手填干支 > 手填年份推算 > 从原文里抠**。为什么手填优先：原文里可能同时抄了生卒两个干支（「康熙戊寅生，乾隆庚戌卒」），让程序去猜哪个属于哪个，早晚会猜错。

反过来，从原文反推公元年分三层，从可信到推测：

| 原文写法 | 依据 | 结果 |
|---|---|---|
| `乾隆壬寅（1735）` | 明写的四位年份 | 1735 |
| `康熙三十七年` | 年号 + 年数 | 1662 + 37 − 1 = 1698 |
| `康熙戊寅` | 年号 + 干支，在年号区间内找唯一的戊寅年 | 1698 |
| `戊寅` | 干支六十年一轮，定不了年 | 留空 |
| `康熙年间` | 没有年数也没有干支 | 留空 |

年号表只收明清与民国（`ganzhi.js` 里的 `ERAS`）。再往上的朝代年号重名太多（「天启」「天顺」都有人用），与其算错不如留空——**空着让人自己填，比填一个错年份好**。

干支与中文世次的实现只有一份（`renderer/ganzhi.js`，UMD 包装），浏览器和 Node 导出共用。分两份写，早晚会出现「界面显示甲子、导出的 Excel 写乙丑」。

### 10. 删除是级联的，而且必须二次确认

删一个人，默认连他的子嗣一起删。理由：父辈没了、子嗣还挂在树上，会变成一群「无祖之家」浮在根层，看起来比「删多了一点」更让人摸不着头脑。

但有两条例外：

- **外支的配偶只解婚、不删人**（和导入时的规则一致）。删掉别支的女儿，等于让别人的谱凭空缺人。
- 删除前先弹窗列清单：要删几个人、会解除几段婚配、其中有几个人是「别支嫁进来的」。看清了再点确认。

### 11. 布局方向是参数，不是两套代码

纵向（上→下）和横向（左→右）共用同一套 tidy tree：布局时只算「主轴坐标」和「侧轴坐标」，最后一步再按 `orient` 映射到 `x/y`。分两套代码写，两边的间距、配偶框位置、包围盒迟早会走偏。

世次只标注在节点框内（第二行「三世」），不做节点外的标尺。曾做过「每代一条淡线 + 一世/二世…」的标尺，按用户要求去掉了：框内已有标注，尺子反而显得杂。分层数据（`levels`）保留，供导出与测试用。

### 12. Excel 也是零依赖手写

`src/core/xlsx.js` 自己做 zip（store + deflate）、CRC32、`[Content_Types].xml` 和四张 sheet 的 OOXML，文本用 `inlineStr` 直接内联，不需要 `sharedStrings`。理由和 PDF 一样：**多一个库就多一个十年后失效的地方**。

导出的四张表：**人物**（一人一行，26 列，含生卒的年份/干支/原文三份）、**婚配**（一段婚姻一行）、**父子**（一条父关系一行，兼祧占两行）、**说明**（导出时间、范围、字段解释）。房支一列写的是「张德昌（二世）」而不是 `branch_id` 那串 uuid——导给自家人看的表，得能读懂。照片只标「有 / 空」，不把 base64 塞进单元格：表格是拿来核对的，不是相册。

### 13. 照片存 base64 进库，不建图片目录

一人一张，存在 `person.photo`（`data:image/…;base64,…` 的 data URL）。配偶也是 `person` 行，所以「配偶节点也能传」不是特例，是同一条代码路径。

**为什么不存文件路径**：库要能被整个拷走、被 `.zupu` 包整支交换。一旦照片在库外，就会出现「谱还在、照片全丢」的经典故障——换台电脑、换个目录、备份只备了 `.db`，图就没了。一个自用软件，不值得为省几百 KB 去引入这种脆弱性。

配套的四个约束：

1. **上传前先压**：超过 500KB 的图在浏览器里画到 canvas，长边压到 1200px 转 JPEG(0.85)；小图原样存，不碰 png 透明背景。
2. **服务端兜底上限 3MB**（base64 字符串 4MB），超了直接拒并说明原因——前端压缩被绕过（老浏览器、直接调接口）时不能把库撑爆。
3. **格式白名单**：只认 png/jpg/gif/webp 的 base64，别的 `data:` 一律拒。存进来的东西将来是要渲染进 `<img>` 的，白名单比校验更省心。
4. **保存人物不碰照片**：`savePerson` 的 UPDATE 语句里没有 `photo` 列。照片是点「上传」即时入库的，走的是 `setPhoto`，改备注、改生年不会顺手把照片抹掉。

照片跟着 `.zupu` 包走（`package-io.js` 的 person 列白名单已含 `photo`，`import-replace.js` 的 upsert 也写了）——整支导入到另一台电脑，照片一起过去。

## 五、已知限制（有意为之，不是 bug）

| 限制 | 原因 / 后续 |
|---|---|
| 不做字段级冲突裁决 | 按你的决策：整段替换，行为完全可预测，没有「有时合并有时覆盖」的模糊地带 |
| 不做人物合并界面 | 同上：同一个人两边各建一次，导入即以锚点为准 |
| 安装包未做代码签名 | Windows SmartScreen / macOS Gatekeeper 会弹「未知发布者」，自家用点「仍要运行」即可；要消掉得买证书（一年几百到几千元） |
| 谱书排版尚未接入 | 现有 PDF 是「一整张图封进单页」的图页，可打印悬挂，但不是文字排版；谱书要等专门模块 |
| 无 OCR | 竖排繁体异体字的校对成本通常高于直接录入 |
| 「配偶框」最多显示两位 | 一夫多妻超过两位时，多余的暂不在图上表达（数据里都在） |
| 年号反推只到明清与民国 | 更早的朝代年号重名多，算错比算不出更糟；可直接手填公元年 |
| 浏览器调试版必须让 `npm run dev` 的窗口一直开着 | 关掉窗口 = 没有后端，界面顶部会挂一条红条提示，点「重试」可在服务恢复后重连。**改了 `src/` 下的代码必须重启该窗口**（无热重载），否则新接口不存在，表现为「删除 / 导出 Excel 点了报错」 |
| 删除没有回收站 | 软删除标记还在库里，但界面上没有「最近删除」入口，误删要靠导入前快照恢复 |

## 六、下一步建议顺序

1. **把界面用到自己家族的真实数据上**——先录 200 人，会立刻暴露字段够不够用
2. 人物字段按老谱栏目补齐（字号、行第、墓向、迁徙、功名、事迹）与照片附件
3. 校对工作台：代次断层、同名同辈、跨届次变更清单（行业普遍短板，也能省交付人力）
4. 谱书排版导出（欧式 / 苏式两套固定版式，不做自由排版）
5. 打印级导出 + 纸质归档（数据寿命要长过代码）

## 七、数据安全三件套（已在代码里）

1. **导入前自动快照**：`data/backups/backup-*.db`，保留最近 20 份
2. **精确撤销**：只回滚那一次导入，之后你自己录的内容不动
3. **完整导出**：`.zupu` 是明文 JSON，二十年后不用这个软件也能读

> 顺带一句：纸是最可靠的备份格式。每年把全谱导出打印一份存起来，成本几百块。
